# 権限分岐の比較試験

Issue #161 のサイト権限取得経路を扱う。単純な主体IDの結合から進め、GetPermissionsで確認した５分岐を独立した合成データとSQL生成で再現する。本体コードやSQL文字列を取り込まず、製品の権限処理を変更しない。

## 再現した分岐

| 分岐 | 比較する条件 |
| --- | --- |
| 組織 | サイトの権限継承先とPermissionsを結合し、組織IDと有効状態で選別 |
| 組織経由のグループ | 有効グループ、所属組織ID、有効組織を結合 |
| ユーザー経由のグループ | 有効グループ、所属ユーザーID、有効ユーザーを結合 |
| 個人 | 正のユーザーIDが指定ユーザーと一致 |
| 公開 | UserId=-1 |

各分岐内の重複を除き、分岐間はUNION ALLで保持する。アプリ側のビット演算による集約の代わりにMAXを使わない。試験は取得行の多重集合を照合し、権限付与の最終判断やログイン可否を再実装しない。

## キーとデータ

独立した７表を使い、検索に関係する次のキー構成を再現する。

- Sites: TenantId・SiteId・UpdatedTimeの主キーとSiteId索引。
- Permissions: ReferenceId・DeptId・GroupId・UserIdの主キー。TenantId列を勝手に追加しない。
- Users / Depts / Groups: TenantIdと各IDの主キー、有効状態またはIDの必要な逆引き。
- GroupMembers: GroupId・DeptId・UserId・ChildGroupの主キーと組織・ユーザー・グループの逆引き。
- GroupChildren: GroupId・ChildIdの主キーとChildId・GroupIdの逆引き。

本体全列・全標準索引・クラスタ化・キー方向まで一致させた物理レプリカではない。ログインID等、この検索に関係しない標準索引は含めない。型はDBごとの整数・日時・真偽値を使う。

400サイト・２テナントを用意し、継承先の共有、同じ組織の重複所属、有効/無効組織・グループ・ユーザー、個人・公開権限を組み合わせる。テナント1の組織所属ユーザー、組織なし、テナント2、無効組織/ユーザーという４つの架空文脈を評価する。無効ユーザー文脈はSQL境界の試験であり、実際にログイン可能とするものではない。

期待値は合成レコードのC#照合で分岐ごとに重複排除し、結合後の重複数と順序までSQL結果と照合する。GroupChildrenの親方向・子方向も標準キーで取得できることを確認する。

## 候補と出力

標準のみ、Sites(TenantId,InheritPermission,SiteId)のみ追加、Permissionsの各主体ID・ReferenceId・PermissionTypeを主体ごとに１本だけ追加、全４本を追加した６段階を比較する。段階間で追加索引を取り外し、単独の効果と全体の効果を分離する。各段階で統計更新を行い、型付きパラメータでウォームアップ後５回実行する。

各追加索引の容量を記録する。SQL Serverは使用ページ数、PostgreSQLは索引リレーションサイズ、MySQLはInnoDBの索引統計ページ数による推定値。表全体や標準索引の容量ではない。

権限100行追加、全272行の権限値更新、継承先１件分の権限８行削除、１テナント200サイトの継承先変更を比較する。各操作をロールバック方式とコミット方式でウォームアップ後５回測定し、影響行数も検証する。時間は実行開始からDML完了まで、コミット方式のみコミット完了まで含む。トランザクション開始・ロールバック・コミット後のデータ復元は計測外で、両方式を同じ費用として扱わない。復元後の検索結果も独立した期待値と照合する。追加専用の架空参照先にはサイトがなく、追加行の影響は検索結果の件数だけでは判断しない。

小規模で固定幅の合成データのため、実環境の競合、ログ耐久性、索引の肥大化、長期の更新量は再現しない。

`permission-workload-<DBMS>.json`へReports（検索件数・時間・実行計画）、Writes（更新時間）、IndexSizes（個別容量）を保存し、CI成功時のArtifactにも含める。SQL ServerはSTATISTICS XML、PostgreSQLはEXPLAIN ANALYZE BUFFERS、MySQLはEXPLAIN ANALYZE。接続情報や実環境レコードを保存しない。

この試験だけでは追加索引を自動採用しない。GetPermissionsByIdやPermissionsWhere等の他経路、実データの広い列・物理配置、規模や分布が異なる場合の費用対効果は残件として扱い、#161 / #145を閉じない。

## 合成試験での採否

2026-11-01のローカルDocker環境での１回の比較。時間は５回の中央値（ms）、検索はテナント1の組織所属ユーザー文脈、更新は272行の権限値更新とコミットを含む。他文脈・操作・個別候補はJSONへ保存する。

| DBMS | 標準の検索 | 全候補の検索 | 標準の権限更新 | 全候補の権限更新 | 追加４本の合計容量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| SQL Server | 5.42 | 4.93 | 5.63 | 16.57 | 128 KiB |
| PostgreSQL | 3.94 | 5.52 | 2.69 | 6.09 | 128 KiB |
| MySQL | 5.85 | 3.33 | 7.90 | 11.38 | 64 KiB（推定） |

検索が改善するケースでも、権限更新の負担が増える。DB間で検索の傾向も一致せず、固定実行順や計測ノイズの影響も残るため、全環境への自動追加は採用しない。特定環境での有用性を否定するものではなく、実クエリ・読み取り指標・更新頻度を含めて別途判断する。
