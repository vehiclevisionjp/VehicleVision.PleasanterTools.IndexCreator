# 権限比較の標準キー補正

## 補正の範囲

Issue #194（親 #161 / #145）。PermissionWorkloadTestsとRecordPermissionWorkloadTestsの基準を補正する。認可処理や製品の索引候補・適用対象の変更ではなく、合成比較の型と関連キーの補正である。

参照日: 2026-11-02。固定参照 `664c833b144d9da9b6bb58e60f7e48eb01141e58` の定義・生成経路を事実確認し、本体のコードやDDLをコピー・依存・ビルド対象にしない。

| 項目 | 補正前 | 補正後 |
| --- | --- | --- |
| 旧５分岐のPermissionType | DB・C#がint | DBがbigint、期待値と読取もlong |
| 個別権限のマスク | DBはbigint、C#とパラメータはint | C#がlong、マスクのパラメータはInt64。主体IDはInt32のまま |
| SQL Serverの日時 | datetime2 | 標準のdatetime |
| MySQLの日時 | timestamp | 標準のdatetime(3) |
| Sites主キー | 全DBで更新日時の方向なし | TenantId,SiteId,UpdatedTime。SQL Server / MySQLは更新日時降順、PostgreSQLは昇順 |
| SitesのSiteId逆引き | 非一意 | 一意 |
| MySQLのUsers / Depts / Groups | TenantId,ID主キー | ID単独主キーとTenantId,IDの非一意索引 |
| GroupChildren | 主キーとChildId,GroupIdの逆引き | GroupId単独の標準索引も共存 |

SQL Server / PostgreSQLのマスタ主キーはTenantId,IDのまま。Permissionsの主キーはReferenceId,DeptId,GroupId,UserId。GroupMembersの主キーはGroupId,DeptId,UserId,ChildGroup、逆引きはDeptId,GroupId・UserId,GroupId・GroupId。GroupChildrenはGroupId,ChildId主キーに上記の通常索引を持つ。ItemsのID主キーを重複索引へ置き換えない。

## 値とDBメタデータの照合

32bitを超える正の合成値 `1L << 40` と既存の下位ビットを組み合わせる。これは保存・転送・ビット判定の型境界を検証するための値であり、新しいPleasanterの権限種別を定義するものではない。

５分岐では公開権限の値に上位ビットを含め、全分岐の多重集合・有効状態・テナント境界の既存照合を継続する。権限値の更新・commit/rollback・復元後に、検索で返らない行も含め全権限行を照合する。

個別取得では公開条件の相関EXISTSに上位ビットを含むマスクを渡し、実際に真になるケースを独立した期待値と照合する。サイト/個別の合成結果も64bitで読む。権限値の変更と復元後の全行照合も64bitで行う。

`PermissionBaseline`は試験表作成後にSQL Serverのsysカタログ、PostgreSQLのpgカタログ、MySQLのinformation_schemaからキーを読み、主キー/通常索引の区別・一意性・列順・方向を検証する。PermissionTypeはinformation_schemaでもbigintと照合する。DDL文字列に指定があるだけで確認済みとはしない。

出力には `BaselineVersion: 2` と `Baseline` を追加し、計測対象の関連キーとPermissionTypeの実際の型を保存する。既存のReports / Writes / IndexSizesは維持する。実レコードや実環境のカタログを保存する機能ではない。

## 再計測の扱い

旧資料の2026-11-01の数値は補正前の条件の履歴として残す。新しいキー・型・上位ビットによって行幅・容量・計画が変わり得るので、前の数値との速度比を製品の改善率とはしない。再現する場合は出力のBaselineVersionを確認する。

通常の専用DB統合試験を3DBで実行し、同じ既存の検索・候補段階・更新試験で再計測する。結果が一致することと索引が有用であることは別の判定であり、この補正だけで主体索引やサイト継承索引を自動採用しない。

## 2026-11-02の再測定

ローカル専用DBの全統合チェックはSQL Server 19761 / PostgreSQL 19766 / MySQL 19768、単体は1006チェック成功。主キー・関連索引・bigint型をカタログから照合し、5分岐と個別権限の両成果物にBaselineVersion 2を保存した。

５分岐はテナント1・組織所属ユーザー文脈の1,200行取得。時間はウォームアップを除く5回の中央値（ms）、更新は全272権限行の変更とcommitを含む。

| DB | 標準の検索 | 全4候補の検索 | 標準の更新 | 全4候補の更新 | 追加候補の合計容量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| SQL Server | 4.32 | 3.80 | 4.06 | 23.91 | 128 KiB |
| PostgreSQL | 3.37 | 3.17 | 2.86 | 4.02 | 128 KiB |
| MySQL | 4.25 | 2.56 | 6.36 | 7.52 | 64 KiB（推定） |

個別権限は4,000件・サイト偏在のgroup-members文脈で合成6行を取得。更新は先頭50レコードの権限値変更とcommitを含む。追加は主体側3索引で、重複Items索引を含めない。

| DB | 標準の検索 | 主体3候補の検索 | 標準の更新 | 主体3候補の更新 | 追加候補の合計容量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| SQL Server | 8.00 | 3.50 | 4.40 | 5.46 | 720 KiB |
| PostgreSQL | 3.01 | 3.51 | 2.52 | 2.94 | 808 KiB |
| MySQL | 1.49 | 1.71 | 5.39 | 6.56 | 720 KiB（推定） |

この時間差を補正自体の性能改善や全環境への保証にしない。同じ補正後の条件内でもDB・経路で傾向が異なり、容量と更新費用が増える。単独候補・他文脈・存在判定・実行計画はJSONへ保存する。固定実行順、キャッシュ、全列幅等の制約は残り、この結果だけで共通索引を自動追加しない。

## 残る再現範囲の制限

検索に関係するキーの補正であり、本体の全列幅・無関係な通常索引・Identity/既定値・履歴/削除表・認証・最終権限ビット集約・画面全体の試験ではない。SitesのReferenceType/FormやUsersのLoginId/SCIM等、この比較表にない列の索引は再現しない。個別権限試験はGroupChildrenの再帰展開を行わない。データ規模と偏りは従来どおりで、全ての分布を網羅するものではない。
