# 管理画面の索引調査

Issue #145 の途中結果。管理系テーブルは通常のレコード用SiteId索引と異なるため、現在の自動適用へ一律に追加しない。３DBの比較検証は [#161](https://github.com/vehiclevisionjp/VehicleVision.PleasanterTools.IndexCreator/issues/161) で追跡し、この文書だけで調査完了とはしない。

## 操作と候補の対応

| 操作 | 検索経路 | 判断・次の確認 |
| --- | --- | --- |
| Users編集の前後移動 | TenantIdとView条件で件数確認後、閾値内の対象をView順・UpdatedTime順で取得 | TenantIdとIDの標準キーは日時順全体のカバーとは異なる。条件と件数別に評価 |
| Depts / Groups編集の前後移動 | TenantIdとView条件、件数上限、UpdatedTime順 | 小規模表ではSortやScanが安価な場合がある。無条件に索引を増やさない |
| 権限一覧 | Permissions.ReferenceIdで絞り込み、複数キーで並べ替え | ReferenceId先頭の標準主キーと照合。並びの差だけで追加しない |
| サイト権限評価 | Sites.InheritPermissionとPermissions.ReferenceId、ユーザー・組織・グループ結合 | 権限評価を管理画面固有の負荷と混同しない。結合方式とOR/UNION全体を測る |
| グループ所属・子グループ | GroupMembersの組織・ユーザー逆引き、GroupChildrenの親子逆引き | 結合列の順序と標準索引を比較し、重複追加を避ける |
| サイト差分・階層 | TenantIdとUpdatedTime、ParentId等の別条件 | TenantId/SiteId/UpdatedTimeのキー順では更新日時の範囲が先頭範囲とは限らない |
| システムログ | ログ日時・種別等の絞り込み、ID参照、前後移動 | CreatedTimeの標準索引、実際の検索頻度、書込負荷を評価。件数だけで追加しない |

部分一致・列の式・任意ORは通常索引一つでカバーしたと扱わない。アプリ処理やロック待ちも別に測る。

Users / Depts / Groupsは[標準キーを共存させた比較](管理マスタの一覧と前後移動の比較試験.md)で、COUNT・狭い投影・広い投影・件数上限を分けて評価する。MySQLの主キー差も反映したが、本体全列・既定JOIN・画面全体の再現ではない。

Sitesは[階層と更新差分の比較](Sitesの階層と更新差分の比較試験.md)、SysLogsは[一覧と保持期限の比較](SysLogsの一覧と保持期限の比較試験.md)で関連する標準キーを揃えた。ID投影やCOUNTの改善を、幅あり取得・閾値で省略される取得・画面全体へ一般化しない。SysLogsは追記と保持期限削除の費用も保存し、新しい索引の自動採用は見送る。

## 自動適用前に必要な設計

具体的な範囲・命名・再利用・削除・停止条件は[管理系共通索引の採用と管理方針](../_documents/管理系共通索引の採用と管理方針.md)へ整理した。この設計文書だけで他の管理表が適用対応になったとは扱わない。

管理系はサイト単位のレコード件数閾値では選別できない。テナントごとの件数・検索条件と、物理表全体の更新コストを分けて判断する。全サイト共用索引の所有権・名前・定義ハッシュと、同じ表を複数候補から共有する方法を定義する。

現行のReadIndexes・ValidateColumns・管理名判定・Reconcilerの対象表を拡張し、欠損列・定義衝突・同時実行では停止する必要がある。削除は明示pruneのみ、標準索引は変更しない。利用者独自索引がカバーする場合の再利用も必要。

SQL Server/PostgreSQL/MySQLで、標準索引と候補の共存、結果一致、再計画Keep、負荷・容量、候補不採用を確認した後に製品対応を判断する。今回、管理系索引の自動作成・削除は実装していない。
