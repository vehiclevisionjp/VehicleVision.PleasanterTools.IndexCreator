# 管理系検索の合成比較試験

この文書は初期の代理表による比較基盤の記録。後続の専用比較と基準補正を含む2026-11-02の[採否と検証範囲](管理系索引の採否と検証範囲.md)を現在の判断とする。

Issue #161 の比較基盤。標準キーを模したTenantId・RecordIdの主キーと、所有者・更新差分・親階層・権限逆引きの追加候補を、独立した架空表で比較する。本体の全管理テーブル・標準索引を再現したものではない。

## 実行

通常の `scripts/test.ps1 -Dbms SQLServer`、`PostgreSQL`、`MySQL` の結合試験に含む。専用検証DBだけを使う。実運用の接続情報は渡さない。

`AdminWorkloadFixture`は４テナントを使い、small-uniform（400件、テナントと所有者が均等）、larger-skewed（4,000件、テナント1と所有者1への偏りあり）の２シナリオを別々の表作成から実行する。件数と分布を同時に変えるため、それぞれの影響を単独に切り分ける実験ではない。

テナント、所有者1、所有者19、０件、別テナント、更新差分、親階層、権限主体、グループ所属、権限０件の10条件を、UpdatedTime・RecordId順で取得する。頻出・希少というケース名は条件値の識別名であり、均等シナリオでは所有者間の頻度は同等になる。各条件をウォームアップ後５回実行し、前後一致に加えて、元データから独立計算した順序付き期待値、想定した空・非空、テナント境界を検証する。候補使用や特定の速度改善率を成功条件にしない。

`AdminLogFixture`はテナント列を持たない別表で、シナリオに合わせて400件または4,000件の架空ログを使う。種別分布も均等と5%の希少種別を切り替える。CreatedTime降順・RecordIdの一意索引とID索引を基準に、Kind・CreatedTime降順・RecordIdの候補を比較する。実SysLogsのクラスタ化・主キー・全列を再現した表ではない。期間のみ、頻出種別、希少種別、０件の４条件を追加し、日付境界と種別分布から独立に計算した順序付き期待値にも照合する。管理レコードと合わせて14検索条件になる。

権限を模したReferenceId・SubjectId主キーの表と、GroupId・UserId主キーとUserId逆引きを持つ所属表を使う。実際のユーザー・組織・グループ権限のUNION全体を再現したものではない。

比較はstandard（標準のみ）、owner、updated、subject、parent、log（それぞれの候補１本のみ）、candidate（５本全部）の７段階。前段階の追加索引を削除してから次を作るため、個別段階に他の候補は残さない。各段階で同じ14条件を評価する。固定された順序の影響は残り、完全に独立したDBスナップショットの比較ではない。

各段階で100件のINSERT、１テナントのOwnerId更新、同テナントのDELETEを、rollbackとcommitのモード別にウォームアップ１回と計測５回実行する。WritesのModeがcommitならClientMsはSQL発行からCommitAsync完了まで、rollbackならSQL発行から実行完了まででロールバック時間を含まない。

コミット後は追加行の削除、更新値の逆更新、削除した架空行の再挿入でデータを復元する。復元費用は計測に含まない。各段階の検索結果が基準と一致することを確認する。復元に伴うページ配置・ログ・キャッシュへの影響は残るため、本体の更新経路全体を評価したものとはしない。

ログ表への100件追記も同じ回数で比較する。候補追加によるログ書込コストは、検索時間と別の採否判断材料として扱う。ログ索引の候補は自動適用機能へ追加していない。

各段階の前にSQL ServerはFULLSCANで統計更新、PostgreSQLはANALYZE、MySQLはANALYZE TABLEを実行する。サンプリング方式やDB間の最適化器の差は残る。

試験終了時に架空表を削除する。製品の対象表・候補生成・自動適用の変更はない。

## 保存結果

テスト実行ファイルと同じディレクトリの`admin-workload-SQLServer-<scenario>.json`、`admin-workload-PostgreSQL-<scenario>.json`、`admin-workload-MySQL-<scenario>.json`へ、各条件の件数・５回のクライアント経過時間・中央値・計画を保存する。出力は合成データのみで、接続文字列を保存しない。

CIのDB試験成功時は`admin-workload-SQLServer`、`admin-workload-PostgreSQL`、`admin-workload-MySQL`のArtifactにも保存する。保持期間内に計画・個別容量・更新時間をダウンロードして比較できる。実データを使うツールの出力をこのArtifactへ混ぜない。

SQL ServerはSHOWPLAN_XMLによる推定計画。PostgreSQLはEXPLAIN ANALYZE BUFFERS、MySQLはEXPLAIN ANALYZEによる実行時の計画。推定と実測を混同せず、DBをまたいでコスト値を比較しない。測定時間には通信と全結果の読取が含まれる。

SQL ServerのSqlServerRuntimeIoには、ウォームアップSELECTのSTATISTICS IOメッセージを保存する。推定計画とは別の実行時情報であり、出力が得られることもテストする。言語依存の文章を機械的に数値へ変換しない。

Sizesはログを含む４つの架空表と全索引の合計容量で、個々の候補の大きさではない。SQL Serverは使用ページ数、PostgreSQLはpg_total_relation_size、MySQLはinformation_schema.tablesのDATA_LENGTHとINDEX_LENGTHを合計する。MySQLは推定値として扱い、DB間で同じ意味・精度の指標とはしない。

IndexSizesは作成した各候補の容量を別に記録する。SQL Serverはその索引の使用ページ、PostgreSQLはpg_relation_size、MySQLはANALYZE後のmysql.innodb_index_statsのsizeをページサイズで換算する。MySQLでは検証用管理ユーザーにこの統計表の参照権限が必要で、値は推定として扱う。いずれも作成直後のサイズであり、長期運用の断片化や最大容量を予測するものではない。

標準キーの測定後に候補を追加して測るため、キャッシュ・コンパイル・実行順序の影響を排除した厳密な性能試験ではない。短い時間差を製品の改善保証に使わない。

## 初期段階の残件（履歴）

この代理表だけの段階では #161 と親 #145 を完了扱いにしなかった。以下は当時の項目であり、対応済みの範囲と再現しない制約の現在の区別は上記の採否資料を参照する。

- 本体各管理表の実際の標準索引・権限分岐を再現する。ログの全列・物理配置も追加評価する。
- 件数と偏りを独立に変える追加シナリオや、実行順を変えた評価を行う。
- 単独候補の測定結果を基に、実際の検索頻度と更新頻度を含めて採否を判断する。
- 差異に基づき候補の採用・不採用を決め、製品の管理名・スキーマ検証・差分管理を設計する。
