# 管理系検索の合成比較試験

Issue #161 の第一段階。標準キーを模したTenantId・RecordIdの主キーと、TenantId・OwnerId・UpdatedTime・RecordIdの追加候補を、独立した架空表で比較する。本体の全管理テーブル・標準索引を再現したものではない。

## 実行

通常の `scripts/test.ps1 -Dbms SQLServer`、`PostgreSQL`、`MySQL` の結合試験に含む。専用検証DBだけを使う。実運用の接続情報は渡さない。

`AdminWorkloadFixture`は４テナント・4,000件。テナント、頻出所有者、希少所有者、０件、別テナントの５条件を、UpdatedTime・RecordId順で取得する。各条件をウォームアップ後５回実行し、前後で同じ順序の結果になることを検証する。候補の使用や特定の速度改善率を成功条件にしない。

試験終了時に架空表を削除する。製品の対象表・候補生成・自動適用の変更はない。

## 保存結果

テスト実行ファイルと同じディレクトリの`admin-workload-SQLServer.json`、`admin-workload-PostgreSQL.json`、`admin-workload-MySQL.json`へ、各条件の件数・５回のクライアント経過時間・中央値・計画を保存する。出力は合成データのみで、接続文字列を保存しない。

SQL ServerはSHOWPLAN_XMLによる推定計画。PostgreSQLはEXPLAIN ANALYZE BUFFERS、MySQLはEXPLAIN ANALYZEによる実行時の計画。推定と実測を混同せず、DBをまたいでコスト値を比較しない。測定時間には通信と全結果の読取が含まれる。

標準キーの測定後に候補を追加して測るため、キャッシュ・コンパイル・実行順序の影響を排除した厳密な性能試験ではない。統計の更新方式も明示制御していない。短い時間差を製品の改善保証に使わない。

## 残件

この段階では #161 と親 #145 を完了扱いにしない。

- 本体各管理表の実際の標準索引を再現し、サイト差分・階層、権限結合、所属逆引き、ログ検索を追加する。
- 件数・偏り・テナントごとの分布と統計更新を制御し、実行順の影響を評価する。
- SQL Serverの実行時読み取り量、各DBの更新負荷と索引容量を比較する。
- 差異に基づき候補の採用・不採用を決め、製品の管理名・スキーマ検証・差分管理を設計する。
