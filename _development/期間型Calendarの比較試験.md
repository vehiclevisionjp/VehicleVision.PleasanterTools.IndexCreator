# 期間型Calendarの比較試験

Issue #173。開始が期間内、終了が期間内、開始・終了が表示期間を包含する、という全ORを独立した架空表で比較する。単独の日付索引を、全ORのカバーと表示しない。

## 再現範囲

`PeriodCalendarWorkload`はSiteId・RecordIdの主キーと、NULLを許すDateA・DateBを持つ。Results / Issuesの全列・全標準索引・物理配置のレプリカではなく、期間条件のアクセス経路を比較する専用表。本体のコード・SQL文字列・実レコードを取り込まない。

400行・３サイトの均等データと、4,000行・サイト1へ偏ったデータを、表の再作成から別々に試す。件数と分布を同時に変えるため、両者の影響を単独に切り分ける実験ではない。通常の短い期間に加え、長期間の包含、開始/終了の片側NULLと両側NULLを含める。

狭い期間、広い期間、全行が期間外となる期間について、サイト1・別サイト2・存在しないサイト99を評価する。境界の23:59:59.997と、その1ミリ秒後を区別する。表示期間は架空の変換済み日時で、UIのタイムゾーン処理や日付計算は再実装しない。

期待値は元レコードとC#のNULL比較から独立に計算する。端点、包含、NULLの代表行が意図どおり含まれることも確認する。SQLに並べ替えは追加せず、読み取り終了後に検証側でIDをソートして多重集合を照合する。通常一覧用のソートをCalendarの性能評価へ混入させない。

## 比較する索引

標準段階、SiteId・DateAのみ、SiteId・DateBのみ、両方の４段階。段階間で追加索引を取り外し、架空表をTRUNCATEして同じ順序・値を再投入する。各段階で統計を更新し、型付きのサイト・日時パラメータでウォームアップ後５回検索する。検索を更新試験より先に測定し、前段階の更新・復元による表の膨らみを検索比較へ持ち越さない。

日時列はSQL Serverのdatetime2(3)、PostgreSQLのtimestamp(3)、MySQLのdatetime(3)。SQL ServerはSTATISTICS XMLによる実行時計画、PostgreSQLはEXPLAIN ANALYZE BUFFERS、MySQLはEXPLAIN ANALYZEを保存する。クライアント時間は通信と結果読み取りを含み、検証用ソートを含まない。計画の選択や一定の改善率をテスト成功条件にしない。

既存の`PeriodCalendarTests`は別に維持し、Planner由来の２候補について列検査・作成・再計画Keepを３DBで確認する。一般APIへの非混入、期間レビューの明示指定、動的スクリプトの抑止は既存の単体試験で検証する。

## 容量と更新

各追加索引の容量を記録する。SQL Serverは使用ページ数、PostgreSQLは索引リレーションサイズ、MySQLはInnoDB統計ページ数による推定値。容量は各段階の更新測定前に取得する。

50行追加、IDが100以下で開始日がある行の日付１日変更、50行削除を、コミット方式とロールバック方式でウォームアップ後５回測定する。日付変更は開始・終了の両方が対象で、NULLは維持する。影響行数を検証し、コミット後は逆更新や架空行の再挿入・削除で復元する。復元行数に加え、段階の最後に全レコードのサイト・ID・日付・NULLが元データと一致することも検証する。

時間はDMLと、コミット方式ではコミット完了までを含む。トランザクション開始、ロールバック、復元時間は含めない。データ復元は論理値に限り、物理配置・空き領域・キャッシュ・ログを初期状態へ戻すものではない。段階の固定順、測定のノイズ、統計方式のDB差も残る。

## 保存と判断

専用検証DBの結合試験で実行し、終了時は架空表を削除する。実行ファイルのディレクトリへ`period-calendar-workload-<DBMS>-<scenario>.json`を出力する。Reportsは検索件数・時間・実行計画、Writesは更新時間、IndexSizesは個別容量。CI成功時の管理系Artifactにも含める。接続情報や実環境レコードは保存しない。

実行時間だけで採用せず、読み取り指標・対象範囲・容量・更新頻度と合わせて判断する。この試験は狭い投影の専用表であり、実際のCalendarのタイトル結合・全投影列・View条件・権限・UI全体の速度を保証しない。

## 比較結果と採用範囲

2026-11-01のローカルDocker環境の例。larger-skewedのサイト1・狭い期間（512行）について、標準と両索引追加を比較した。時間は５回の中央値（ms）。日付更新はIDが100以下で開始日がある行の変更とコミットを含む。

| DBMS | 検索ms（標準→両方） | 読取指標（標準→両方） | 日付更新ms（標準→両方） | 追加２本の容量 |
| --- | --- | --- | --- | --- |
| SQL Server | 5.51→3.39 | 論理読み取り19→19 | 6.35→7.14 | 240 KiB |
| PostgreSQL | 1.95→1.44 | 計画ルートの共有ヒット29→35、共有読み込み0→0 | 4.60→3.76 | 96 KiB |
| MySQL | 2.21→1.84 | 主キーのSiteId検索で3,467→3,467行から選別 | 12.24→10.13 | 256 KiB（推定） |

SQL Serverの単独候補も論理読み取り19、MySQLの単独候補も同じ主キー検索だった。PostgreSQLの単独候補は共有ヒット29、両候補は狭い期間35・広い期間29。検索のクライアント時間が短くなっても、全ORの読み取り削減を一貫して確認できなかった。更新時間の傾向もDBで異なり、短い時間差を恒常的な性能差としない。小規模シナリオ・他サイト・空検索・個別候補はJSONへ保存する。

期間型Calendarは明示された`plan /include-period-calendars`のレビュー対象として維持し、自動適用や既定の候補生成へ広げない。２本は各日付分岐を検討するための候補で、全ORのカバー・性能改善を保証するものではない。一般APIへの非混入、動的条件の抑止、apply・prune禁止を維持する。

この判断は全環境で索引が無効という結論ではない。特定環境で採用する場合は実際の全OR・投影・権限・View・更新頻度を含めて計画と費用を確認する。標準列・標準索引・本体クエリを変更せず、式索引やクエリ書換えを自動導入しない。
