# 拡張サーバースクリプトの解析境界

Issue #138 の結論: ファイル・Extensionsテーブルの拡張本文に固定Getがあっても、実行文脈・順序・共有状態が確定しないため候補化は追加せず、理由付き診断を維持する。拡張SQLの索引は作成者が管理する。

## 本体との照合

確認日: 2026-11-01。参照コミット: `664c833b144d9da9b6bb58e60f7e48eb01141e58`。事実確認専用であり、本体のコピー・流用・依存追加は行わない。

| 論点 | 本体の挙動と解析への影響 |
| --- | --- |
| DB読込 | 初期化時にDisabled=falseの拡張を名前順で既存のパラメータリストへ追加。名前だけで入力元間の重複や全順序は確定しない |
| 本文 | DBの非空Bodyは設定内本文を上書き。解析側のファイルは隣接本文が存在すれば空でも優先し、不在ならJSONへ戻る |
| 適用先 | 組織・グループ・ユーザー・サイト・レコード・コントローラー・アクション・列・名前指定・Disabledで選別。正のサイトリストだけで実行条件は確定しない |
| イベント | 適用された拡張とサイト内の有効スクリプトを連結し、イベントやShared、Functionalize、TryCatch等を扱う |
| Include | 結合されたスクリプト群から本文を展開。個別ASTだけでは共有状態や展開後の順序を証明できない |
| キャッシュ | 結合結果を再利用する経路がある。現在のDB・ファイル読取を本体への即時反映と同一視しない |

入力の列挙順は、本体の全イベントの実行順序を再現する契約ではない。本文の呼出を診断できても、確定した候補とは扱わない。将来候補化するには入力元間の順序、適用文脈、イベント、Include、共有・ラッパー、先行処理の副作用を確定する契約が必要。今回は設計・診断の検証を成果とする。

## 安全条件

- 無効・削除は次回読取へ反映。ファイル本文だけの削除はJSON本文への復帰と区別する。
- 正のサイトリストで影響候補を限定する。未指定・負指定・不明なスコープは全サイトを要確認とする。
- 名前・本文をログへ出さず、入力元・通し番号・理由を診断する。
- 同名拡張を入力元間で勝手に統合しない。
- 読取失敗や不正構造は停止し、空入力へ置き換えない。
- 削除・無効化から自動DROPを生成しない。plan専用・prune禁止を維持する。

## 検証範囲

３DB共通の合成設定で、固定Getを含む拡張も確定候補にしないこと、ファイルとテーブルで同じ境界になること、無効化後に不確定サイトから外れることを確認する。既存の結合試験は本文優先、有効・無効・削除、読取失敗を確認する。本体の全ユーザー・イベントの実行再現は未実施。
