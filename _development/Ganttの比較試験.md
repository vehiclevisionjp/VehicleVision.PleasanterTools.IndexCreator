# Ganttの比較試験

Issue #174 の比較試験と採否記録。Ganttの開始CASEと終了日付補正式を含む期間重複ORを、独自の架空表で比較する。製品は保存ViewのDefaultModeがGanttの場合、専用候補を生成できていないことを診断する。通常Viewフィルターの候補とGantt期間式のカバーは別に扱う。

## データと比較

４千件・３サイトのStartTime、CompletionTime、CreatedTimeを持つ架空表を作る。開始と終了に独立にNULLを含め、期間包含・端点・期間外を生成する。標準段階のキーはSiteId・RecordId、比較候補はSiteId・StartTimeとSiteId・CompletionTimeの２本。本体Issuesの全列・標準索引・物理配置を再現したものではない。

開始式は、参照で確認した単純CASEのNULL比較の意味を維持して独自に組み立てる。NULLのStartTimeをCreatedTimeへ補うCOALESCE相当の式には変更しない。終了の日付補正はSQL ServerのDATEADD、PostgreSQLのinterval、MySQLのDATE_ADDで0日と-1日を試す。

確認したEditorFormatの対応は`Ymd`だけが-1日、その他（未指定を含む）は0日。２通りの試験でこの補正分岐を網羅する。本体の日時パラメータ生成は開始のUTC変換と終了の日数加算・3ミリ秒減算を行う。試験は変換済みの架空期間を使い、タイムゾーン変換自体を再実装しない。

固定の期間に対する３分岐のORを実行し、前後とも独立したC#のNULL比較・日付演算で求めた期待値と照合する。日時列は３桁精度、型付き日時パラメータを使い、終了日の23:59:59.997と直後の23:59:59.998を区別する。ウォームアップ後５回のクライアント時間と計画を保存する。SQL ServerはSTATISTICS XMLによる実行時計画、PostgreSQLはEXPLAIN ANALYZE BUFFERS、MySQLはEXPLAIN ANALYZEを使う。時間には通信と結果読み取りを含む。

## 容量と更新

追加２本の容量を個別に記録する。SQL Serverは使用ページ数、PostgreSQLは索引リレーションサイズ、MySQLはInnoDB統計ページ数による推定値。

200行追加、NULL以外の開始を持つ3,200行の開始・終了１日変更、200行削除を、コミット方式とロールバック方式でウォームアップ後５回比較する。DMLの影響行数を検証し、コミット後は架空データを復元して行数を再検証する。その後の検索を独立した期待値と照合する。

時間はDMLと、コミット方式ではコミット完了までを含む。トランザクション開始、ロールバック、復元時間は含めない。更新頻度・競合・ログ耐久性・長期の肥大化を実環境と同等に再現するものではない。

## 出力と制約

テスト実行ファイルのディレクトリへ`gantt-workload-<DBMS>.json`を出力する。Reportsに検索結果・時間・計画、Writesに更新時間、IndexSizesに容量を保存する。CI成功時には管理系比較と同じArtifactに保存する。データは架空のみで、接続情報は含めない。

固定実行順・小さい架空表での時間差や、索引が使用されたことだけで採用とはしない。View条件・権限・結合の全組合せ、実際の本体UI、異なる物理配置での性能は保証しない。この試験は開始・終了の単純列索引を一律に自動追加するかどうかの判断に使う。

## 採用方針

2026-11-01のローカルDocker環境での比較例。時間は５回の中央値（ms）。検索は補正0日の全OR、更新は3,200行の日付変更とコミットを含む。

| DBMS | 標準の検索 | 追加後の検索 | 標準の日付更新 | 追加後の日付更新 | 追加２本の合計容量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| SQL Server | 3.09 | 2.47 | 25.22 | 85.78 | 240 KiB |
| PostgreSQL | 2.23 | 2.04 | 21.51 | 33.78 | 96 KiB |
| MySQL | 9.41 | 7.42 | 68.74 | 135.39 | 240 KiB（推定） |

SQL Serverは補正0/-1日とも追加前後で標準の主キー経由・11論理読み取り。PostgreSQLの計画ルートの共有バッファヒットは100から105（共有読み込みは0）、MySQLは追加前後とも主キーのSiteId検索で1,333行から選別した。読み取り削減を一貫して確認できず、日付更新は遅くなった。

実行順は固定で、データ復元は論理値の復元に限る。更新に伴う物理配置・空き領域やキャッシュまで初期化しておらず、時間差を索引だけの因果効果と断定しない。追加容量を記録した時点も更新測定の前で、長期容量の上限ではない。

Gantt専用候補の自動追加は採用せず、理由付き診断と通常View条件の解析を維持する。開始CASE・終了日付補正・全ORを単純な日付索引でカバーできると表示しない。標準列・クエリの変更や、無検証の式索引追加も行わない。

これはGantt画面全般の最適化完了や、特定の追加索引が全環境で無効という結論ではない。個別の実クエリで改善が確認できた場合は、View・権限・更新頻度まで含めた別の採用判断とする。
