# 管理マスタの一覧と前後移動の比較試験

Issue #161 / #145。Users・Depts・Groupsを別々の架空表で比較し、従来の単純なTenantId・RecordId表と区別する。標準索引と共存した場合の候補効果、COUNTと行取得の違い、前後移動の件数上限を評価する。本体のコード・SQL文字列・定義ファイルをコピーせず、製品の認証・画面処理を変更しない。

## 参照版から確認したキー

全て昇順の標準キーを次のように用意する。表名・索引名は試験専用で、標準の管理名やハッシュを流用しない。

| 表 | SQL Server / PostgreSQLの主キー | 共存させる標準索引 |
| --- | --- | --- |
| Users | TenantId,UserId | UserId,TenantId / LoginId,ScimExternalId,ScimId,TenantId,UserId / ApiKey,TenantId,UserId / LoginId単独の一意索引 |
| Depts | TenantId,DeptId | DeptCode / Disabled |
| Groups | TenantId,GroupId | Disabled / LdapGuid,ScimExternalId,ScimId |

MySQLはID単独主キーとし、元のTenantId・IDのキーを非一意索引として追加する。列JSONだけから主キーを推測せず、CodeDefinerのPkMySql分岐を確認した。

同じIx序数の列は通常のJSON読取順と安定した並べ替えを照合した。LoginIdの一意索引は、複合Ixとは別に生成される。カスタム定義やDefinition.jsonによる別の読取経路まで同じ構成と保証するものではない。

文字列は列定義の上限を使い、SCIM・API・GUID列のNULLを含める。組織コードはSQL Serverのnvarchar(1024)、PostgreSQLのvarchar(1024)、MySQLは索引対象の長い文字列に適用される短縮規則に合わせvarchar(760)。UpdatedTimeはSQL Serverのdatetime、PostgreSQLのtimestamp、MySQLのdatetime(3)。API列の値は明示的な架空文字列で、実際の認証情報ではない。

全標準列・Comments等の広い列、Identity、既定値・制約、履歴/削除表、カスタム定義を再現する表ではない。非索引のPayload列に256文字を置き、狭いID投影と広い投影の違いを見る。このPayloadは本体の特定の列や実データの平均幅を表すものではない。

## データと検索

400件の４テナント均等分布と、4,000件のテナント1偏在を別々に作る。無効状態の分布も変える。件数・分布を同時に変えるため、各要因を単独に切り分ける実験ではない。更新時刻は行ごとに異なり、同日時の順序を勝手にID順と保証しない。

テナント、無効状態、コードの完全一致・前方一致・部分一致、別テナント、0件、明示ID順を９条件で評価する。通常はUpdatedTime降順。広い投影はコード・Payload・更新日時も返す。SQLの条件・並びに対して、元データから独立に計算したID列と順序を照合する。

広い投影はページングしない検索の費用比較であり、本体の一覧ページや既定JOINを再現したものではない。UsersJoinDefault、関連列、任意の実行時View、画面全体の速度は別の評価が必要となる。

コード条件は独立した完全一致/LIKE条件であり、本体が列に関数や結合を加える経路まで同じとは仮定しない。

## 前後移動の条件

本体で確認した件数判定の境界を試験側で構成し、COUNTと取得SQLの費用を分けて保存する。認可やUI処理の製品実装ではない。

- Usersは管理権限がない文脈なら現在IDだけとなる。管理可能な文脈ではCOUNTを実行し、件数が上限以下なら行を取得する。上限が0以下でもCOUNT自体は実行する。
- Depts / Groupsは上限が正の場合だけCOUNTを実行し、その上限以下なら行を取得する。
- 現在IDが結果にない場合は補完する。試験では無効状態の条件で除外される現在IDを使う。

上限-1・0・参照版の既定500・一致件数の直前/同数/直後を評価する。有効行が上限を超えるケースでは一覧を取得しない。保存するRowMs=0は取得を実行しなかった結果で、索引による高速化ではない。COUNTにも実行時計画を保存する。

## 候補・更新と出力

標準のみ、TenantId・UpdatedTime降順・ID、TenantId・Disabled・UpdatedTime降順・ID、両候補の４段階。段階間で候補を取り外して表をTRUNCATEし、同じ順序・値を再投入する。統計更新後に検索と件数判定を実行し、その後で更新試験を行う。ウォームアップ後５回を計測する。

候補の個別容量を、SQL Serverの使用ページ数、PostgreSQLの索引サイズ、MySQLのInnoDB統計ページ数による推定値で記録する。SQL ServerはSTATISTICS XML、PostgreSQLはEXPLAIN ANALYZE BUFFERS、MySQLはEXPLAIN ANALYZEを保存する。一定の速度や索引選択を成功条件にしない。

50行追加・先頭100行の更新時刻変更・50行削除を、コミット/ロールバック別にウォームアップ後５回比較する。影響行数を検証し、コミット後は逆操作で復元する。段階の最後に、標準索引用の補助列やNULLも含む全フィクスチャ値を照合する。

時間はSQL実行と、コミット方式ではコミット完了まで。開始・ロールバック・復元費用は計測外。検索前は初期化するが、更新中の物理配置変化、ログ、キャッシュ、競合、固定実行順の影響までは除去しない。本体の保存・関連更新全体の費用ではない。

`directory-workload-<DBMS>-<kind>-<scenario>.json`へReports（検索）、Switches（件数判定と取得）、CountPlans（COUNT計画）、Writes（更新）、IndexSizes（候補容量）を出力し、CI Artifactへ含める。専用検証DBでのみ実行し、終了時は架空表を削除する。

候補は一律に自動追加しない。件数判定だけを実行する場面、標準索引で足りる場面、広い投影や部分一致を区別する。2026-11-02の[採否と検証範囲](管理系索引の採否と検証範囲.md)に他経路・未検証の物理条件と、新規採用を見送る判断を記録した。将来製品化する場合の所有権と明示pruneは正式な管理方針に従う。

## 合成試験の判断例

2026-11-01のローカルDocker環境。4,000件・偏在のテナント1には有効行が2,600件あり、既定上限500の前後移動では３表ともCOUNT後の行取得を省き、現在IDだけを返した。この場面に、強制的に全行取得した測定の改善率を当てはめない。

SQL Serverで標準とDisabled・日時順候補を比較すると、UsersのCOUNTと狭い有効行取得は論理読み取り263→10、広い投影は263→263だった。Depts / Groupsの狭い取得は235/253→10だが、COUNTは既存索引で9、候補追加後10だった。取得とCOUNTを同じ効果としない。

PostgreSQLのCOUNTの計画ルート共有ヒットはUsers 182、Depts 160、Groups 167で候補追加前後とも不変、共有読み込みは0だった。MySQLはUsers / GroupsのCOUNTに候補のカバー参照を使った一方、Deptsは既存索引同士の交差を使い続けた。SQL Serverだけの結果を他DBの保証にしない。

| DBMS | UsersのDisabled・日時順候補容量 | 100行更新＋コミットの中央値ms（標準→候補） |
| --- | ---: | ---: |
| SQL Server | 112 KiB | 10.77→8.97 |
| PostgreSQL | 176 KiB | 13.72→7.75 |
| MySQL | 112 KiB（推定） | 7.85→13.87 |

時間はウォームアップ後５回の中央値で、固定順や短時間のノイズを含む。更新費用の傾向も一致せず、一定の速度改善・悪化を一般化しない。他の条件・段階・表・小規模シナリオはJSONに保存する。採否は実際のCOUNT、投影、件数上限、検索頻度と更新量を照合して個別に決める。
