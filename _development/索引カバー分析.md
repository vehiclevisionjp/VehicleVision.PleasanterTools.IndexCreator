# 保存ビュー条件と DB 構造の索引カバー分析

確認日: 2026-10-09。固定参照コミット `8d29c7bd110c2487ad4b39bd34dafaf0ba66373b` の本体 SQL 生成と、IndexCreator v0.1.1 の候補生成を比較した。本番 DB のスキーマ・データ・実行計画を取得した分析ではない。以下の追加候補は v0.2.0 の変更で、v0.1.1 の正式配布物には含まれない。

## DB 構造と SQL の照合

Results / Issues / Wikis はサイトごとの独立テーブルではなく、SiteId を持つ共有の物理テーブル。候補は通常の列索引として作り、実 DB の列の存在と、既存の通常 B-tree の先頭キー・方向・prefix・opclass を照合する。同じ定義はサイトをまたいで共有する。標準索引や列の変更は不要。

本体の保存ビューには、ColumnFilterHash 以外から生成するフィルタがある。Own は Manager と Owner の OR、Issues の NearCompletionTime は CompletionTime の範囲、Overdue は Status と CompletionTime の AND 条件になる。UseNegativeFilters と ViewFilters_... の組み合わせで否定される場合は、肯定条件の候補として扱わない。

並べ替えは本体の Column.IsNullValue に従い、NULL の置換やリンク先の値を必要とする場合がある。索引だけでその式に対応できる根拠がないため、この変更では式索引・計算列を追加しない。

| 条件 | v0.1.1 の不足 | 追加した候補例 |
| --- | --- | --- |
| 自分が担当 | Own を診断するが担当者条件の候補を作らない | SiteId, Manager, UpdatedTime DESC, ID DESC と Owner の同形候補 |
| Issues の期限が近い | NearCompletionTime を解析しない | SiteId, CompletionTime |
| Issues の期限超過 | Overdue を解析しない | SiteId, CompletionTime と SiteId, Status |
| 複数の範囲・前方一致 | JSON に現れた最初の列だけを採用 | 各範囲列につき、SiteId, 完全一致列..., 範囲列を生成 |

Own と範囲条件の併用時は、OR 分岐ごと・範囲列ごとの候補になる。範囲の後ろの並べ替えカバーや、複数の候補の同時使用は保証しない。候補本数が増えるため、実行計画と更新負荷による選択が必要。部分一致、任意の OR、リンク先条件、全文検索、Items.Title の追加索引は引き続き対象外。

## 一次資料

### リンク選択肢・項目連携の追加解析

本体コードは参照専用とし、SQL や標準索引・列・テーブルを変更しない。追加の通常列索引だけを IndexCreator 側で計画する。

- `Links[].View` はリンク元の保存ビューではなく、リンク先の選択肢を取得する条件。リンク先 Results / Issues の通常フィルタと明示的な並べ替えを候補にする。本体の既定は Items.Title 順なので、UpdatedTime のタイブレーカを付けない。Wiki 本文の選択肢には適用しない。
- `RelatingColumns[].Columns` の隣接項目から親・子のリンク先を求め、子マスタにある親へのリンク列を本体と同じ編集項目順で選ぶ。編集項目順が省略され、候補が複数ある場合は推測せず診断する。連携の段数ごとに処理し、重複候補を統合する。
- 単一選択の本体 SQL は `SiteId = 子サイトID AND TRY_CAST(Class列 AS bigint) IN (...)`（SQL Server）など。`SiteId, Class列, ID` を追加することで、SiteId での絞り込みとサブクエリの投影列を索引に持たせる。Class列の変換は残余条件であり、変換値による seek をサポートしたとは扱わない。MySQL の prefix は変換前の値全体を保持しないので、読み取り全体のカバーも保証しない。
- 複数選択の SQL は `LIKE '%"ID"%'`。項目連携用の追加候補は作らず診断する。既存の通常リンク候補とは独立して扱う。連携先の件数には `/min-records` を適用し、リンク元の件数によって連携先の解析を省略しない。
- `ColumnFilterExpressions` は未対応として明示的に診断する。ルックアップの値転記は ID による取得のため、転記元列すべてへの索引追加はしない。

## 検証

単体チェック125件で OR 分岐、否定の有効・無効、期限列のテーブル制限、複数範囲、JSON の列順に依存しない命名、並べ替えカバーを主張しないことを確認した。SQL Server 2025 Developer / PostgreSQL 15 / MySQL 8.4 の専用 IndexCreatorTest DB で列検査、索引作成、カタログの往復、再実行時の Keep、標準索引の保護を確認した。検証用スキーマは必要列を持つ最小構成で、本体の全スキーマ・権限・実運用データを再現するものではない。

Own の合成データ試験は10万行で、Manager または Owner が42の2000行を抽出する COUNT クエリを比較した。初回を除いた5回の中央値は、SQL Server 13.170 → 13.083 ms、PostgreSQL 15.076 → 1.933 ms、MySQL 142.049 → 125.715 ms。追加した候補が必ず速くなる結果ではなく、特にこの SQL Server の条件では改善が確認できない。性能の閾値を試験の合格条件にはしていない。

SQL Server は実行計画を採取する再試験でも11.488 → 12.922 msで、Table Scan が選ばれた。計画確認の処理はベンチマークに残した。この最小スキーマはヒープであり、本体の標準主キー構成とは異なる。実際の Azure SQL の結果へこの時間や計画を一般化しない。

実際のサイトのカバー率を百分率で示すには、本番の保存ビューと利用頻度・データ分布・実行計画が必要。ここで確認したのは追加条件の候補生成と専用 DB での動作であり、全業務クエリのカバー率ではない。
