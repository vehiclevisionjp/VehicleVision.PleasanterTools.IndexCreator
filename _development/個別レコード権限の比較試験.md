# 個別レコード権限の比較試験

2026-11-02に[関連する標準キーと64bit値の補正](権限比較の標準キー補正.md)を行った。現行出力はBaselineVersion 2。以下の2026-11-01の測定値は補正前の履歴として扱う。

Issue #161 / #145。Items経由の個別権限取得と、権限条件の相関EXISTSを独立した架空表で比較する。本体コード・SQL文字列・実レコードを取り込まず、製品の権限処理を変更しない。

## ２つの経路

本体の認証済み呼出側はサイト権限を取得し、正のレコードIDが現在サイトIDと異なる場合にGetPermissionsByIdの断片を追加する。サイト側はSites.InheritPermission、個別側はItems.ReferenceIdからItems.SiteId→Sitesのテナント境界を経てPermissionsへ結合する。試験はこのSQL合成を独立に構成する。

個別IDは呼出側の固定数値展開に合わせて架空の数値リテラル、テナント・組織・ユーザーとEXISTSのマスクは型付き整数パラメータを使う。組織・組織所属グループ・ユーザー所属グループ・個人・公開の５分岐内はDISTINCT、分岐間とサイト/個別の間はUNION ALLで保持する。C#の元データ照合で行の多重集合を検証し、MAX等の集約に置換しない。

存在判定は、ReferenceIdと必要な権限ビットを外側のPermissions行へ指定し、PermissionsWhereの相関EXISTSを比較する。組織・グループのテナント/有効状態、主体IDが0ではない条件、同じ参照先の公開権限を別々に評価する。５分岐の取得とは異なり、ユーザー所属分岐にUsers.Disabledの検査を勝手に追加せず、公開分岐も外側のUserId=-1だけへ単純化しない。期待値は別のC#述語で計算する。

これはSQL境界の試験で、認証・特権・レコード範囲・最終ビット集約まで含む認可処理ではない。無効ユーザーの文脈はSQLの差を確認する架空ケースで、ログイン可能という意味ではない。統合サイト用の別条件は対象外。

## 表とデータ

検索に関係する標準キーを７表に用意する。

- Sites: TenantId・SiteId・UpdatedTime主キーとSiteId逆引き。
- Items: ReferenceId主キーとSiteId・ReferenceId索引。同じIDだけの追加索引を不足と誤認しない。
- Permissions: ReferenceId・DeptId・GroupId・UserId主キー。PermissionTypeは標準定義と同じbigint。
- Depts / Groups / Users: SQL Server / PostgreSQLはテナントと各IDの主キー、MySQLはID単独主キーとテナント・IDの通常索引。有効状態またはIDの必要な逆引きも保持する。
- GroupMembers: GroupId・DeptId・UserId・ChildGroup主キーと組織/ユーザーからの逆引き。

全列・全標準索引・クラスタ化・キー方向・Identityの完全なレプリカではない。GroupChildrenの再帰展開も含めない。

２テナント・４サイトで400件の均等分布と4,000件のサイト偏在を別々に生成する。件数と分布を同時に変えるので、両者の影響を単独には切り分けない。権限なし、組織内重複、所属グループ、個人、公開、無効な主体、無効ユーザーの所属、複数ビットを組み合わせる。

11文脈で２経路を実行し、分岐内/分岐間の重複、所属、有効/無効、主体IDが0、継承のみ、別テナント、テナント境界、対象なし、サイト自体の文脈を検証する。

## 候補と計測

標準のみ、Items.ReferenceIdの重複索引のみ、PermissionsのDeptId/GroupId/UserId・ReferenceId・PermissionTypeを各１本、主体側３本の組合せ、の６段階。重複Items索引は費用確認用の反例で製品へ追加しない。組合せ段階にも含めない。

前の候補を取り外してItemsとPermissionsをTRUNCATEし、同じ順序・値を再投入する。統計更新後、更新試験より先に検索する。ウォームアップ後５回のクライアント時間を保存し、検証用ソートは時間に含めない。SQLに余分なORDER BYは追加しない。

SQL ServerはSTATISTICS XML、PostgreSQLはEXPLAIN ANALYZE BUFFERS、MySQLはEXPLAIN ANALYZEを保存する。容量はSQL Serverの使用ページ数、PostgreSQLの索引サイズ、MySQLのInnoDB統計ページ数による推定値。索引選択や特定の改善率を成功条件にしない。

50件のItems追加、先頭50レコードの権限値更新、50件のItems削除を、ロールバック/コミット別にウォームアップ後５回比較する。影響行数を照合し、コミット後は削除・逆更新・再挿入で復元する。段階の最後にItemsとPermissionsの全値も照合する。

時間はDMLと、コミット方式ではコミット完了まで。開始・ロールバック・復元は計測外。Itemsだけの追加/削除は保守費用を分ける試験で、本体の保存・関連削除全体ではない。更新中の物理配置変化、キャッシュ、ログ、競合、固定実行順の影響は残る。

## 保存と採否

専用検証DBで実行し、終了時は架空表を削除する。`record-permission-<DBMS>-<scenario>.json`のReportsに検索件数・時間・計画、Writesに更新件数・時間、IndexSizesに個別容量を保存し、CI Artifactへ含める。実環境の接続情報・設定・レコードは含めない。

ItemsのID主キーを重複索引で置き換えず、主体側の候補も合成試験だけで自動採用しない。2026-11-02の[採否と検証範囲](管理系索引の採否と検証範囲.md)に新規採用を見送る判断を整理した。広い投影、他の標準索引、同時更新、統合サイトや管理画面の全クエリは未検証のままであり、今回の比較完了から性能保証を導かない。

### 合成試験の比較例

2026-11-01のローカルDocker環境。4,000件・サイト偏在のgroup-members文脈で、サイト/個別の合成６行を取得する場合。時間は５回の中央値（ms）。更新は先頭50レコードの権限値変更とコミットを含む。

| DBMS | 検索ms（標準→ID重複→主体３本） | 読取指標（同順） | 権限更新ms（標準→主体３本） | 追加容量（ID重複 / 主体３本） |
| --- | --- | --- | --- | --- |
| SQL Server | 15.29→10.88→6.29 | 論理読み取り180→180→123 | 5.76→8.71 | 72 / 720 KiB |
| PostgreSQL | 6.43→5.03→7.09 | 計画ルートの共有ヒット78→78→66、共有読み込みは全て0 | 3.60→4.41 | 104 / 808 KiB |
| MySQL | 1.75→1.79→3.55 | 各計画はJSONに保存。DB間で同じ読取単位とは扱わない | 7.92→9.89 | 80 / 720 KiB（推定） |

ID重複索引はSQL ServerとMySQLの当該段階の全計画で選ばれず、PostgreSQLでは一部で選ばれても上の共有ヒットは減らなかった。選択されたこと自体を採用根拠にしない。

SQL ServerのGroupId候補単独では合成の論理読み取り123、存在判定は標準と同じ10だった。PostgreSQLの主体３本は合成の共有ヒットを減らしたが、クライアント時間の改善とは一致しない。経路・DB・更新費用を分けて評価し、一定の効果を全環境へ一般化しない。小規模・他の文脈・個別候補の全結果はJSONへ保存する。
