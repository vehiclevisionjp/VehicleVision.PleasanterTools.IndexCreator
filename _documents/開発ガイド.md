# 開発ガイド

本書はソースを変更・検証する開発者向けです。製品の導入・接続設定・操作は [導入手順](導入手順.md) と [利用ガイド](利用ガイド.md)、製品の入口は [README](../README.md) を参照してください。

必要なものは .NET 10 SDK、Git、3 DB を検証する場合は Docker と PowerShell 7。SDK は global.json、依存は packages.lock.json に固定する。

実行時のコンソール出力は英語固定です。Azure の開発者コンソール（Kudu）のエンコーディング制約で日本語が文字化けするため、進行表示・確認入力・警告・エラーを英語で書き、DB ドライバーの例外文を直接出さないでください。ドキュメント・コードコメント・Issue・PR は日本語で書きます。

```powershell
git clone --recurse-submodules https://github.com/vehiclevisionjp/VehicleVision.PleasanterTools.IndexCreator.git
cd VehicleVision.PleasanterTools.IndexCreator
dotnet restore --locked-mode
dotnet build -c Release --no-restore
pwsh -File scripts/test.ps1
```

チェックは依存フレームワークを持たない実行型テストプロジェクトで、失敗時は非ゼロ終了。**`dotnet test` はこれらのチェックを実行しない**。必ず scripts/test.ps1 またはテストプロジェクトの dotnet run を使う。

3 種類の DB を個別に検証する:

```powershell
pwsh -File scripts/test.ps1 -Dbms SQLServer
pwsh -File scripts/test.ps1 -Dbms PostgreSQL
pwsh -File scripts/test.ps1 -Dbms MySQL
docker compose --profile '*' down -v
```

専用 compose プロジェクト `indexcreator-test`、ポート 51433/55432/53306、DB 名 IndexCreatorTest を使用する。結合テストはこの DB 名以外を拒否する。検証用の公開パスワードだけを使い、外部へポートを公開しない。再実行する前に失敗した検証 DB の残存テーブルを専用コンテナの再作成で取り除く。

オフラインの候補を確認する:

```powershell
dotnet run --project src/IndexCreator -c Release -- plan /sites examples/sites.json /dbms SQLServer
```

開発中の既定配置は配布環境と異なるので、本体への接続は `/p` で明示する。VS Code の tasks と launch にビルド・チェック・各 DB・オフライン計画を登録している。

配布 ZIP は次のコマンドで作る。OS・アーキテクチャ共通のフレームワーク依存版（`-portable.zip`）と SHA256 が artifacts/package に出る。SDK・本体コード・検証 DB は配布しない。

```powershell
dotnet restore --locked-mode
pwsh -File scripts/package.ps1
```

Docker 版は `docker build -t indexcreator .`。本体の Parameters フォルダを含むディレクトリを読み取り専用でマウントし、`/p` で指定する。

CI は Release ビルド、単体チェック、3 DB 結合チェック、配布 ZIP の作成、参照ソース混入の検査を行う。CodeQL は独立のワークフロー。`v*` タグでは下書きリリースを作り、検証した ZIP を添付する。初版では正式リリースタグを自動作成しない。

## ソース構成と開発資料

- `src/`: 独立 CLI。Pleasanter のプロジェクト参照なし。
- `tests/`: 単体・専用 DB 結合チェック。
- `_reference/`: 参照専用の Pleasanter 本体サブモジュール。
- `_documents/`: 利用者向けの導入・利用・運用と、開発者向けの設計・開発運用・リリース。
- `_development/`: 出典と検証結果の開発記録、本体の画面操作による E2E のスクリプト（`e2e/`）。配布しない。
- `.github/`: CI・CodeQL・監査・PR 規約・参照更新・共通規約。

設計は [アーキテクチャ方針](アーキテクチャ方針.md)、Actions とエージェント運用は [開発運用](開発運用.md)、公開は [リリース手順](リリース手順.md)、確認済み範囲は [検証記録](../_development/検証記録.md) を参照してください。

Node.js 24 は Markdown 検査だけに使います。`npm ci --ignore-scripts` 後に `npm run lint:md` を実行します。書式と内部ファイルリンクを確認し、参照サブモジュールや一時ファイルは対象から外します。実行環境には Node.js は不要です。

## App Service 配置の再現

`pwsh -File scripts/package.ps1` の後、`pwsh -File scripts/appservice-smoke.ps1` で配布 ZIP から検証します。Windows x86 / x64 と Linux x64 に対応し、CI は同じ配布 artifact を取得して実行します。Windows x86 は `-Platform win-x86 -DotnetPath 'C:\Program Files (x86)\dotnet\dotnet.exe'` のように x86 のホストを指定します。CI では公式 dotnet-install.ps1 で .NET 10 の x86 ランタイムだけを一時フォルダへ用意し、PATH は変更しません。

temp の専用領域に site/wwwroot、CodeDefiner、本体、IndexCreator、別の作業フォルダを作ります。既定の兄弟フォルダ解決、/p の絶対パスと空白、-p の互換指定、wwwroot 直下の本体配置、アプリ設定に相当する環境変数、接続失敗時の ASCII のみの出力と秘密値の非表示を確認します。WEBSITE_SITE_NAME と WEBSITE_INSTANCE_ID、Production をプロセスへ渡します。

ローカル再現はフォルダと環境変数・実行の検証であり、Kudu のサーバー実装や Azure のネットワーク・認証・実行制限を再現するものではありません。実際の App Service 上の検証は [検証記録](../_development/検証記録.md) で別に追跡します。

依存更新は Dependabot が develop 宛てに提案する。追加・更新時は直接・間接依存のライセンス、脆弱性、NOTICE と ThirdPartyNotices.txt を確認し、dotnet restore でロックを更新する。

## 合成データによる比較

`pwsh -File scripts/test.ps1 -Dbms PostgreSQL -Benchmark` で専用 DB に10万行を作り、索引追加前後の COUNT の取得結果と中央値を比較する。SQLServer / MySQL も同じ指定に対応する。最初の1回をウォームアップに使い、残り5回の中央値を報告する。時間の合否しきい値は設けない。実運用のデータ分布・同時実行・並べ替え・更新負荷の代替にはしない。検証後に専用の表を削除する。
