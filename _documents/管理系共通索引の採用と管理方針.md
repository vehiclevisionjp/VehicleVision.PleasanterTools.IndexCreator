# 管理系共通索引の採用と管理方針

Issue #145の設計方針。#161の3DB比較を踏まえ、2026-11-02の[採否と検証範囲](../_development/管理系索引の採否と検証範囲.md)を確定した。実装済みのSites更新差分を維持し、他の管理系候補の新規自動採用は見送る。測定可能な候補があることと、製品がその表を管理できることを区別する。この文書で新しい管理系コマンドや自動適用を導入しない。

## 現在の対応と採用判断

| 対象・経路 | 現在の範囲 | 判断と根拠 |
| --- | --- | --- |
| Sitesの更新差分 | `/include-site-delta`で明示したTenantId・UpdatedTimeの共通索引を計画/適用 | 実装済み。通常実行ではSitesをprune範囲へ入れない |
| Users / Depts / Groupsの一覧・前後移動 | 合成比較まで。追加候補の自動計画/適用は未実装 | COUNT、件数上限、投影で効果が異なる。[管理マスタの比較](../_development/管理マスタの一覧と前後移動の比較試験.md)を参照 |
| Sitesの親階層・権限継承 | 調査・合成比較まで。新規自動採用は見送り | 更新差分用の索引を別経路の改善とみなさない。投影・利用文脈・更新費用で差がある |
| Permissionsの主体参照・個別レコード | ５分岐と相関EXISTSを３DBで比較 | DB・主体文脈・更新量で採否が異なる。一律に全候補を追加しない |
| GroupMembers / GroupChildren | 主キー・逆引きの比較 | 標準キーで足りる経路へ重複索引を追加しない。統合・再帰処理全体の保証ではない |
| SysLogs | 日時・種別・前後移動・追記・期限削除の合成比較。新規自動採用は見送り | COUNTの改善を行取得へ一般化せず、DB差・容量・保持期限処理の費用も含めて判断する |
| 拡張SQL | 自動候補生成・作成の対象外 | ファイル/Extensions表に関係なく、クエリ作成者が[手動ガイド](拡張SQLのインデックス設計ガイド.md)に従って保守する |

現行のカタログ読取と列検査はResults・Issues・Wikis・Items・Sitesを対象とする。カタログに読めることが、全ての表の索引を所有・削除できるという意味ではない。管理名判定、候補生成、操作範囲を別々に確認する。

Users等の比較用索引は専用検証DBの架空表だけに作成する。ArtifactのDDLや名前を、そのまま実表の管理機能として案内しない。

## テナントと物理索引の単位

参照版の標準定義では、Sites・Users・Depts・GroupsにTenantIdがあり、Permissions・GroupMembers・GroupChildren・SysLogsにはない。カスタム環境では実際の列も検査する。列のない表へTenantIdを想定して候補を生成したり、列を追加したりしない。

評価する検索件数はテナントや条件ごと、保守費用と容量は物理表全体で扱う。`/min-records`のサイト別件数を、管理表の採用閾値に流用しない。件数だけで候補の必要性も決めない。

共通索引は表全体の通常索引とする。名前の予約ID0は共通用途を識別する値であり、特定テナント・SiteId=0だけのフィルタ索引という意味ではない。同じ物理定義はテナントや呼出元ごとに複製しない。索引の作成は認可処理の実装・代替ではない。

## 所有権と重複判定

現在のSites共通索引は`IX_vvplic_Sites_0_TenantId_<16桁ハッシュ>`の専用形式を使う。他の管理表は現在の管理名判定へ含めていない。

新しい管理系の用途を採用する場合は、実装前に次を確定する。

1. 対象表・論理用途・許可する物理キー定義を列挙する。汎用的な接頭辞判定だけで他の管理表を所有しない。
2. 名前は`IX_vvplic_<表>_0_<用途>_<定義ハッシュ>`を基礎とし、既存の長さ制限と正規形を使う。テナントID・利用者名・設定値は含めない。
3. 表、列順、方向、MySQL prefix、PostgreSQL opclassを比較する。異なる定義を、名前や用途が似ているという理由で同じとみなさない。
4. 新しい共通名前空間について、対象表・用途・ハッシュとカタログ上の定義を検査してから所有を認める。これを現行の全表で既に実装したとは扱わない。
5. 同名の定義衝突は停止する。標準名・独自名の索引をリネームして所有化しない。

有効な通常B-treeが必要な先頭キーを満たせば、標準索引・利用者独自索引をその名前のままKeepとして再利用する。フィルタ・式・無効・不可視・異なる照合条件等を通常索引と同等扱いしない。prefix等の異なる定義の代替性を、現行の保守的な比較を変更せず推測しない。利用者独自索引や標準索引を`/f`で置き換えたり、`/prune`で削除したりしない。

## 操作範囲と削除

| 状況 | 扱い |
| --- | --- |
| 共通用途の明示指定なし | その共通用途の作成・修復・削除範囲へ含めない。現在のSites更新差分がこの方式 |
| 設定の削除・無効化、候補の消失 | それだけで物理索引を削除しない。レビュー専用機能からも削除しない |
| 入力の欠落・読取失敗・不正な設定 | 空の希望集合とみなしてpruneしない。変更を止め、入力不明と0件を区別する |
| 新しい定義への移行 | 必要な作成・検証を先に行い、明示された範囲の不要な所有索引だけを最後に削除する |
| 共通用途そのものの廃止 | 未指定を削除指示にしない。対象用途・名前・定義を明示する廃止手順が必要。現行に削除専用CLIがあるとは案内しない |

追加の管理系オプションを設ける場合も、通常の`/prune`や`/f`へ自動的に範囲を広げない。部分的な対象読取を表全体の完全な希望集合として扱わない。設定変更が物理索引へ与える影響は、希望集合・操作範囲・所有権の３つを揃えて判定する。

現行のSitesは更新差分１用途を前提とした表単位のScopeである。同じSitesへ別の共通用途を追加する場合は、既存用途との干渉も検証し、用途単位のScopeを実装してから対象を広げる。`/include-site-delta /prune`だけで、別用途の共通索引まで不要と判定させない。単に管理名の正規表現や対象表一覧を増やす変更では不十分とする。

## 検査・同時実行・回復

現行の適用には、列名検査、同名衝突停止、セッションロック、作成後のカタログ再検証、削除前のサイト設定再確認がある。新しい管理系の対象を増やすには、候補生成だけでなくカタログ読取・列検査・管理名判定・操作範囲を一緒に拡張する。

管理表の型・照合順序・NULL等の互換性確認は、現行の列名存在検査だけで完了したことにしない。管理設定が通常のSites以外に由来する場合、その入力の変更検出も追加する。現在のSitesスナップショットだけで管理表の全設定を保護できるとは扱わない。

適用はRdsのDisableIndexChangeDetectionを確認し、オンライン処理・ロック待機上限・再試行・キャンセル後の再計画という既存の[運用手順](運用手順.md)に従う。管理表でもオンライン不可を黙ってオフラインへ切り替えない。新規索引の検証失敗時は不要索引を削除せず、再計画で部分適用を確認する。標準索引・列・テーブルの再構成は行わない。

## 採用前の評価条件

比較前後で、SQLの形、投影、JOIN、条件、並び、件数上限/ページング、パラメータの型と値、利用者文脈を揃える。ローカルDECLAREを実際の型付きパラメータと同じ計画と仮定しない。結果件数だけでなく、NULL・重複・順序が必要な場合の順序も照合する。

単一の主体条件だけで決めず、代表的な別テナント・所属なし・公開・空集合を含める。結果差が出た場合はデータ更新やSQL差を切り分ける。よく使う条件で悪化がある候補を、別の１条件が改善したという理由だけで採用しない。

SQL Serverの論理読み取り、PostgreSQLの共有ヒット/読み込み、MySQLの実行行数やループ等をそれぞれ評価し、DB間でコスト値を横並びにしない。時間・容量・実行頻度・更新費用も合わせる。索引が選ばれたことや短い時間差だけを採用根拠にしない。

前後移動ではCOUNTと実際の行取得を分離する。件数上限を超えて取得しない場合に、強制取得の高速化率を当てはめない。新鮮な合成表、固定実行順、狭い投影を、実際の全画面の性能保証としない。

## 検証状況と残る実装条件

現在のSites更新差分は、明示指定、通常pruneからの除外、独自索引の再利用、同名衝突、欠損列、３DBの作成・再計画Keepを既存試験で確認している。これは他の管理表への適用検証を意味しない。

新しい共通用途を実装する場合は、３DBでカタログ往復、無指定時の保護、重複・標準索引再利用、欠損/不正/衝突、候補消失と明示prune、作成失敗時の削除抑止、設定変更、オンライン失敗後の回復を検証する。未検証の用途は候補のレビュー・比較までに留め、実装前に別Issueへ分割する。

今回の比較と未検証範囲は[採否と検証範囲](../_development/管理系索引の採否と検証範囲.md)と各合成試験に記録する。未採用用途の拡張は、必要になった時点で別Issueに採用根拠と上記の適用検証を定義する。公開Issue/PR・配布物には汎用仕様と架空データのみを含める。
