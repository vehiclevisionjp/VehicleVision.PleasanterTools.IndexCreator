# 利用ガイド

## サーバースクリプトの診断

索引の計画・適用時に、サイト設定内の有効な ServerScripts を構文解析します。
`view.Filters` / `view.Sorters` / `view.SearchTypes` の直接代入、`items.Get` 呼出、
オブジェクト内の `ColumnFilterHash` / `ColumnSorterHash` の列を診断として表示します。
件数閾値未満のサイトも診断対象です。検索値・スクリプト本文は表示しません。

これは構文上の参照候補です。同名変数、分岐、別名、外部生成コードの意味は確定しません。
先頭から副作用なしに読み取れる変数宣言と、固定IDを使う
`items.Get(id, JSON.stringify(data))` は、検索先IDとViewの列を関連付けて表示します。
戻り値を変数へ代入する形と、`items.Get(...)` を単独の文で呼ぶ形に対応します。
第2引数に固定のJSON文字列を直接渡す形、先頭で宣言した文字列変数を渡す形も対象です。
JSONはオブジェクト内にオブジェクト型の`View`が必要です。不正なJSON、重複キー
（大文字小文字だけが異なるものを含む）、実行時に組み立てる文字列は確定しません。
スクリプト全体を囲うtryも対応します。最初のGetまでが対象で、途中の再代入・関数呼出・
分岐・別名参照などで確定できなくなれば、通常の未確定診断に戻ります。
検索先が読み込んだサイト一覧に存在するかも表示します。記載のない形は実行時に確認してください。
`plan /include-script-queries` を指定すると、解決できた固定Viewの索引候補を計画へ含めます。
検索先の件数に `/min-records` を適用し、通常の部分一致・結合・式ソートの除外規則を使います。
この機能はレビュー用のplan専用で、適用操作と `/prune` には併用できません。
`/output` で出したDDLは、実行計画・既存索引・更新コストを確認してから扱ってください。
無効なスクリプトと、`ServerScriptsAllDisabled` が有効なサイトのスクリプトは除外し、
構文解析に失敗すると DB 変更前に停止します。

### 解析状態と未解決理由

`plan /include-script-queries` の診断は、`script-view`（View変更）と`script-query`（固定Get）を区別します。
`resolved`は対応範囲を解析済み、`resolved-no-candidates`は解析できても件数閾値や列の規則などで候補がない状態です。
`resolved-no-mutations`は対応本文にView変更がなく、`resolved-no-query`は対応する宣言列にGetがない状態です。
`unresolved`を候補不要と解釈しないでください。

未解決理由には`scope-or-shadowing`、`unresolved-value`、`unsupported-statement-or-operation`、
`shared-script`、`include`、`execution-wrapper`、`settings-loading`、`extension-impact`などを表示します。
View変更の`combined statement #2.then.1`は、対象ハンドラーを保存順で連結した本文の第2文のthen側の第1文です。
元ファイルの行番号ではありません。固定Getは保存配列内のスクリプト序数と、先頭からの文番号を表示します。
固定Getの解析範囲は最初のGetまでで、後続文やcatch / finallyまで検証済みという意味ではありません。

拡張入力の`not-provided`は未指定、`read (0 entries)`は正常に読み取った結果が0件です。
ファイル件数は無効設定も含む読取件数で、テーブルは有効な対象種別の読取件数です。
読取失敗を0件として扱いません。本文・検索値・任意の識別子は診断に表示しません。

### Viewの直接変更

`plan /include-script-queries` は、`WhenViewProcessing` が有効なスクリプトの
`view.Filters.Status = '100';` や `view.Sorters.UpdatedTime = 'desc';` といった
固定文字列の直接代入も扱います。空のViewと各保存済みViewに上書きし、未変更の条件を保持して候補化します。
Sortersはasc / descに加えて数値リテラルと数値文字列の0（昇順）・1（降順）も扱います。
release / 2、未知の値、動的な値は確定せず、その本文全体の候補化を見送ります。
角括弧の固定キーも対象です。実行時のセッション・権限・ユーザー操作は再現しません。
`view.SearchTypes.ClassA = 'ExactMatch';` のような検索方法の変更も、保存済みの検索方法へ
上書きして評価します。PartialMatch / ExactMatch / ForwardMatchと、それぞれのMultiple版に対応します。
SearchTypesは、対応する数値1・2・3・11・12・13のリテラルと数値文字列も扱います。
部分一致は索引キーの候補から除外し、前方一致はDBごとの規則を使います。
未知の検索方法や動的値が含まれる場合、全体の候補化を見送ります。
`view.FilterNegative('Status')` または第2引数が固定の`true` / `false`の呼出も対応します。
第2引数の省略は否定の設定、`false`は解除です。対象は直接代入で扱う列名に限り、
特殊フィルター名や動的な引数は診断に留めます。本体と同様、Filtersの値を反映した後に
明示的な否定指定を適用します。同じ列へ複数回指定すると最後の指定が優先されます。
否定される列は通常の等価条件として索引キーに含めません。
引数なしの `view.ClearFilters()` は、それ以前のフィルター代入と保存済みの条件、全文検索、
Incomplete / Own / NearCompletionTime / Delay / Overdueを解除します。
ソート・検索方法・明示的なFilterNegative指定は保持し、その後のFilters代入を評価します。
文字列・数値・真偽値を固定したconst宣言も追跡します。
例えば `const status = '100'; view.Filters.Status = status;` を直接指定と同様に扱います。
先に宣言した定数への参照も対象です。Sorters・SearchTypesの値とFilterNegativeの引数にも使えます。
Filters・Sorters・SearchTypesの列名も、先に宣言した文字列定数で指定できます。
例えば `const column = 'Status'; view.Filters[column] = '100';` が対象です。
Filters / Sorters / SearchTypesというグループ名と、ClearFilters / FilterNegativeというメソッド名も、
既出の文字列定数で指定できます。`const group = 'Filters'; view[group].Status = '100';` も対象です。
let / var、宣言前の参照、再代入、式の計算、オブジェクト、分割代入、viewの同名宣言は未対応です。
操作名・列名・引数・値の型の制約は直接指定時と同じです。未知の操作名は全体の候補化を見送ります。
角括弧で指定した操作は通常の診断にも表示しますが、そこで定数の解決や実行の確定は行いません。
条件分岐を伴わない `{ ... }` ブロックも32階層まで解析します。内側から外側の定数を参照できますが、
内側の定数は外側や隣のブロックへ持ち出しません。外側の定数と同名の宣言は未解決とします。
条件がtrue / falseまたは既出のbool定数で、各分岐を `{ ... }` で囲むif / elseも扱います。
例えば `const enabled = true; if (enabled) { view.Filters.Status = '100'; }` が対象です。
両側の本文が対応範囲に収まることを検査してから、選ばれた側の変更だけを反映します。
未選択側の未知の処理も除外対象です。実行時の条件、数値や文字列の真偽変換、条件式の計算、
波括弧なしの分岐、else ifは未対応です。分岐と通常のブロックを合わせて32階層までです。
対象の本文全体が対応するconst宣言・代入・FilterNegative・ClearFilters呼出・ブロック・固定分岐だけで構成される場合に限ります。複数ある場合は保存配列の順に
改行で連結して解析し、後の代入が優先されます。スクリプトIDや名前では並べ替えません。
1つでも未対応の分岐・動的値・複合代入・未対応の関数呼出などがあれば、全体の候補化を見送ります。
複数ハンドラーにTryCatchまたはFunctionalizeが含まれる場合、サイト設定読込時の処理・共有スクリプト・
Include・拡張の影響がある場合も診断に留めます。無効なハンドラーは含めません。

### ファイルとExtensionsテーブル

```sh
IndexCreator plan /include-script-queries /extension-path /opt/pleasanter/App_Data/Parameters /extensions-table
```

- `/extension-path` はParametersディレクトリを指定します。`ExtendedServerScripts/**/*.json` と
  `ExtendedSqls/**/*.json` を読み、隣接する `.json.js` / `.json.sql` があれば本文を優先します。
- `/extensions-table` は接続先DBの有効な `ServerScript` / `Sql` レコードを読みます。
  非空のBodyはExtensionSettings内の本文より優先します。SQL Server・PostgreSQL・MySQLで利用できます。
- 両方を同時に指定できます。同名や同じ本文でも自動的に同一視しません。
  名前・本文・パスを表示せず、入力元と通し番号で診断します。
- 拡張サーバースクリプトはASTで検索操作を診断します。拡張SQLは検索列・WHERE・ORDER BYなどへの
  介入フラグを表示し、SQLの実行や任意SQLからの索引生成は行いません。
- 正のSiteIdListだけを持つ設定は対象サイトを限定します。その他の文脈依存条件や負指定、
  テナント・ユーザー・グループ・アクション条件は実行時に確認が必要です。
  影響する可能性があるサイトでは、拡張の実行順序を推測してスクリプト候補を合成しません。
- 入力は実行のたびに読み直します。ファイルやレコードの削除・無効化は次回に反映します。
  JSONファイルが残り本文ファイルだけが消えた場合は、JSON内の本文へ戻ります。
  作成済み索引は削除しません。スクリプト候補と`/prune`の併用は禁止のままです。
- 指定した入力元が読めない場合やExtensionsテーブルが存在しない場合は停止します。
  読めた結果0件だった場合とは区別します。リンクされたファイル・ディレクトリも停止対象です。
  未指定の入力元は読みません。出力にはファイル・テーブルを指定したかと取得件数を表示します。

拡張の診断はplan専用です。ファイルだけなら`/sites`によるオフライン計画でも使えますが、
`/extensions-table`は実DB接続が必要です。拡張SQLは保存先にかかわらず、索引候補生成・
自動作成の対象外です。必要な索引はクエリ作成者が追加・保守します。
[拡張SQLのインデックス設計ガイド](拡張SQLのインデックス設計ガイド.md)を参照してください。
拡張SQL本体の構文・実行計画は解析しません。拡張サーバースクリプト本文からの索引自動生成、
共有・拡張を含む一般的なスクリプトの実行順序の解決は未対応です。

本書は導入済みの IndexCreator を実行する利用者・運用管理者向けです。初回設定は [導入手順](導入手順.md)、サイト変更時は [運用手順](運用手順.md) を参照してください。

## 確認して適用する

```powershell
dotnet VehicleVision.PleasanterTools.IndexCreator.dll plan
dotnet VehicleVision.PleasanterTools.IndexCreator.dll _rds
```

`plan` は DB を変更しません。`_rds` は `apply` の別名で、計画を表示してから `yes` の入力を求めます。自動実行は `/y` を付けます。

```powershell
dotnet VehicleVision.PleasanterTools.IndexCreator.dll _rds /p "C:\web\pleasanter\Implem.Pleasanter" /y
dotnet VehicleVision.PleasanterTools.IndexCreator.dll _rds /p /opt/pleasanter/Implem.Pleasanter /c
```

`/p` は Pleasanter 本体フォルダです。Parameters フォルダは指定しません。空白を含む値は引用符で囲みます。Linux の `/` で始まる絶対パスも使えます。相対パスは作業フォルダ基準です。未指定の場合は実行ファイルの位置から兄弟の本体フォルダを解決するので、別の作業フォルダからでも起動できます。

`/c` は確認のみで、`/y` や `/f` があっても DB を変更しません。`/f` は管理対象の同じ定義を DROP → CREATE で作り直します。CodeDefiner のテーブルを強制変更する指定とは対象が異なります。標準索引は作り直しません。

## 計画の読み方

| 表示 | 意味 |
| --- | --- |
| Create | 不足している候補を作成する |
| Keep | 有効な同名索引または通常 B-tree の既存索引で足りる |
| Repair | 無効索引、または /f で指定した管理索引を再作成する |
| Drop | /prune で不要な管理索引を削除する |
| WARNING | 未対応の条件や、索引キー長などの確認事項 |

管理名は `IX_vvplic_{ReferenceType}_{SiteId}_{用途}_{定義ハッシュ16桁}`。同じ候補を何度実行しても重複しません。実 DB の索引を読み直すため、前回の実行記録ファイルは不要です。コンソールは英語固定です。

## コマンドと引数

| 指定 | 内容 |
| --- | --- |
| plan | 読み取りだけの計画 |
| apply / _rds | 計画を確認して適用 |
| `/p <path>` | Pleasanter 本体フォルダ |
| `/y` | 確認入力を省略 |
| `/c` | 確認のみ |
| `/f` | 同じ定義の管理索引を再作成 |
| `/min-records <n>` | 対象サイトの最小レコード数。既定 10000 |
| `/include-filter-columns` | フィルタ欄に配置した項目も候補にする |
| `/mysql-prefix <n>` | MySQL TEXT キーの先頭文字数。1〜191、既定 100 |
| `/schema <name>` | DB スキーマを上書き |
| `/dbms <name>` | SQLServer / PostgreSQL / MySQL |
| `/offline` | オンライン作成を使わず、ロックを伴う作成を許可する。保守時間帯だけで使う |
| `/lock-timeout <秒>` | DDL 1回あたりのロック待ちの上限。1〜3600、既定 5 |
| `/prune` | 不要な管理索引を削除 |
| `/output <path>` | 検査時点の操作 SQL を保存 |
| `/sites <path>` | エクスポートしたサイト JSON を解析。plan のみ |
| `/exclude-tree <SiteId,...>` | View の対象から、指定サイトとその配下すべてを除外 |
| `/exclude-site <SiteId,...>` | View の対象から、指定したサイトだけを除外 |
| `/names <label\|column>` | 一覧 View の列名。`label` は表示名（既定）、`column` は列名（ColumnName） |

引数の書式は Implem.CodeDefiner と同じで、操作の後ろに `/` で始まるオプションを並べ、値のあるオプションはその次の引数が値です。旧書式の `--` や `-p`、`-y` は使えません。同じオプションを重複して指定するとエラーです。Git Bash では `/p` などがパスとして変換されるため、PowerShell か cmd.exe で実行するか、`MSYS_NO_PATHCONV=1` を設定してください。DB の `_rds` は CodeDefiner 自体を実行しません。言語・タイムゾーン・DB 作成など CodeDefiner 固有の設定は変更しません。

## 初版の対応範囲

サイト設定による候補に加え、Results / Issues / Wikis の表ごとにレコード ID 単独の参照用候補を生成します。これは `/min-records` 未満のサイトでも生成し、既存の先頭 ID 索引が利用できれば `Keep` にします。標準の主キー・一意制約を復旧する機能ではありません。標準構成と差がある場合は、本体のスキーマ管理と分けて確認してください。

Results・Issues の保存ビューの通常の等価・範囲・前方一致フィルタ、関数を伴わない並べ替え、リンク項目、サマリを解析します。自分が担当する条件（Own）は Manager / Owner の OR 分岐ごとに候補を作ります。Issues の期限が近い・期限超過と、複数の範囲条件も候補化します。SQL Server・MySQL では既定並べ替え用の索引も作ります。PostgreSQL では標準 PK が足りるため追加しません。

部分一致、複数選択、Own 以外の任意の OR、否定、リンク先条件、長いテキスト、式索引が必要な並べ替え、親から子への JOIN、Items.Title の追加索引は未対応です。一時的な画面条件・API 条件・拡張 SQL は SiteSettings に残らないため対象外です。未対応のものは診断として報告します。追加すればすべての一覧が速くなるわけではありません。

Own や複数の範囲条件では候補数が増える場合があります。各候補は DB が選択できるアクセス経路であり、すべてが同時に使われることや、検索・並べ替え全体をカバーすることは保証しません。適用前に `plan /output indexes-plan.sql` で本数とキー列を確認し、実行計画・索引サイズ・登録更新の負荷を測定してください。

リンク選択肢の絞り込み条件は、リンク先のマスタにも候補を生成します。項目連携では子マスタの親リンク列とレコード ID を含む候補を生成しますが、本体が行う数値変換は残ります。単一選択でも変換式の索引検索を保証せず、複数選択は部分一致のため専用候補を追加しません。リンク先の件数には `/min-records` を適用するので、小さいマスタも検討する場合は値を下げて計画を確認してください。式条件（`ColumnFilterExpressions`）は未対応として診断します。

SQL Server の分類列は最大キー長 1700 バイトを超える値の登録・更新を失敗させる場合があります。PostgreSQL の B-tree にもサイズの上限があります。MySQL の分類列は先頭部分だけを索引にします。実際の列長と代表ビューの応答を確認してください。

## 稼働中の環境で実行する

業務を止めずに適用できるよう、索引はオンラインで作成します。SQL Server は ONLINE、PostgreSQL は CONCURRENTLY、MySQL は INPLACE / LOCK=NONE を使います。SQL Server 2022 以降と Azure SQL では低優先度でロックを待つため、待機中も業務の更新が先に進みます。

索引や View の変更が他の処理のロックを待つ時間は `/lock-timeout` の秒数までです。上限に達すると変更せずに中止し、間隔を空けて2回まで再試行します。それでも取れない場合は停止し、完了した変更はそのまま残ります。負荷が下がってから再実行してください。PostgreSQL の CONCURRENTLY は業務の読み書きを妨げないため、既存の処理が終わるまで待ちます。SQL Server 2022 以降と Azure SQL の索引作成は、低優先度の待機を分単位でしか指定できないため、1回あたり最大1分待ちます。再試行を含めると最大3分ほどかかりますが、その間も業務の処理は止まりません。

オンライン作成に対応しない SQL Server のエディションでは停止します。ロックを伴う作成を受け入れる場合は、保守時間帯に `/offline` を付けて実行してください。

## DB に接続せず計画する

エクスポート JSON はサイトごとに SiteId、ReferenceType、RecordCount、SiteSettings を持つ配列です。SiteSettings は JSON オブジェクトまたは JSON 文字列に対応します。

```powershell
dotnet VehicleVision.PleasanterTools.IndexCreator.dll plan /sites sites.json /dbms PostgreSQL /output indexes.sql
```

このモードは既存索引と比較しません。SQL の出力は検査時点の差分なので、繰り返し適用には本アプリを再実行してください。

## 実行ログ

起動時の作業フォルダに `logs/VehicleVision.PleasanterTools.IndexCreator_yyyyMMdd_HHmmss.log` を作成します。CodeDefiner と同じ logs フォルダ・製品名と開始日時の形式です。同じ秒に起動した実行は同じファイルに追記します。コンソールの計画・操作結果・エラーを英語で保存し、接続文字列や例外の詳細は記録しません。ログを書けない場合は DB 操作を開始しません。

ログは UTF-8 で保存します。自動削除は行わないため、運用に合わせて保持期間と整理方法を決めてください。SQL View の操作は [サイト View ガイド](サイトViewガイド.md) を参照してください。
